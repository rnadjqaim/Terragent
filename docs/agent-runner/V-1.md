# v-1: terraform agent runner

this is the first design for a terraform runner that sends plan/apply work to an agent over rpc.

the idea is simple: the user can still work from terraform, but the dangerous work is done by a trusted runner. the runner owns cloud credentials, checks policy, locks state, tracks versions, and keeps an audit log.

## why

local terraform is powerful, but it can become risky in teams:

- credentials live on many machines
- people can run `apply` from different environments
- terraform and provider versions drift
- deprecated modules stay around too long
- audit logs are often incomplete
- policy checks happen too late or outside the normal flow

this runner turns terraform execution into a controlled platform workflow.

## architecture

```text
developer
   |
   v
terraform cli / web ui
   |
   | rpc
   v
agent runner gateway
   |
   | auth, policy, versions, deprecations, state lock
   v
terraform agent worker
   |
   | init, validate, plan, apply
   v
cloud provider + remote state
```

## main parts

### control plane

this is the cli or web ui. it creates the run request and streams the result back to the user.

first terraform integration points:

- `internal/command/plan.go`
- `internal/command/apply.go`
- `internal/backend/backendrun`
- `internal/rpcapi`

the best place to start is around the point where plan/apply builds a `backendrun.Operation` and calls `RunOperation`.

### agent runner gateway

the gateway receives the rpc request and decides if the run is allowed.

it handles:

- user identity
- workspace access
- version checks
- deprecation checks
- state locking
- run history
- event streaming
- audit logs

### terraform agent worker

the worker runs terraform in an isolated directory or container.

it handles:

- source checkout
- `terraform init`
- `terraform validate`
- `terraform plan`
- `terraform apply`
- log streaming
- plan artifact upload

### policy layer

policy returns one of four decisions:

- allow
- warn
- require approval
- block

example blocking cases:

- public ssh from `0.0.0.0/0`
- unencrypted storage
- missing production tags
- unsupported terraform version
- deprecated provider version
- deprecated internal module
- protected resource deletion

## rpc shape

the first rpc draft is in:

`docs/agent-runner/agentrunner.v1.proto`

important calls:

- `Handshake`
- `PlanRun`
- `ApplyRun`
- `WatchRun`
- `CancelRun`
- `GetRun`
- `CheckVersions`

## plan flow

1. user runs plan.
2. cli sends a `PlanRun` request.
3. gateway checks auth, policy, versions, and deprecations.
4. worker runs `init`, `validate`, and `plan`.
5. events stream back to the cli.
6. gateway stores the plan result and audit trail.

## apply flow

1. user requests apply.
2. cli sends `ApplyRun` with an approved plan id.
3. gateway checks approval and locks state.
4. worker applies the exact approved plan.
5. events stream back to the cli.
6. gateway stores the final result.

## version management

each workspace can define allowed terraform, provider, and module versions.

example:

```json
{
  "terraform": {
    "allowed": ">=1.8.0,<2.0.0",
    "recommended": "1.13.0",
    "minimum_security": "1.10.5"
  }
}
```

decision rules:

- below `minimum_security`: block
- outside `allowed`: block
- allowed but old: warn
- recommended version: allow

## deprecation management

deprecation notices should be useful, not noisy.

each notice should say:

- what is deprecated
- current version
- recommended version
- deadline
- replacement
- whether it warns or blocks

example:

```text
deprecated module
module: platform/vpc
current: v2.3.1
replacement: platform/network-foundation v3.1.0
deadline: 2026-12-31
decision: warn
```
